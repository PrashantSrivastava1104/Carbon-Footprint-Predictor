## Part 2: Why Each Model Was Chosen

We compared exactly three models because they represent three different families:

| Model | Family | Key Assumption |
|---|---|---|
| Linear Regression | Linear | Target is a weighted sum of features |
| Random Forest | Bagging (ensemble of trees) | Average many deep trees to reduce variance |
| XGBoost | Boosting (sequential trees) | Each new tree corrects the previous tree's errors |

**Why these three?**
- They cover a spectrum from simple→complex.
- Comparing them teaches you about bias–variance tradeoff.
- They are the most common trio asked about in ML interviews.

**Winner: XGBoost** because:
- It achieved the best test R² (0.9721) and CV R² (0.9686).
- Its gradient-boosting approach captures the non-linear interactions in this
  synthetic formula-generated dataset better than linear regression.
- Unlike Random Forest, it did not overfit (train–test gap only 0.0269).

## Part 3: What the Metrics Mean

| Metric | Formula | Plain English |
|---|---|---|
| **R²** (R-squared) | 1 − SS_res / SS_tot | "What fraction of the variance in CO₂e does the model explain?" 1.0 is perfect; 0.0 means the model is no better than predicting the mean. |
| **MAE** (Mean Absolute Error) | mean(\|y_pred − y_true\|) | "On average, how many kg CO₂e/month is the model off by?" Lower is better. XGBoost: **10.53 kg/month**. |
| **RMSE** (Root Mean Squared Error) | sqrt(mean((y_pred−y_true)²)) | Like MAE but penalises large errors more heavily. XGBoost: **14.20 kg/month**. |
| **CV R²** (5-fold cross-validation) | Average R² across 5 non-overlapping test folds | Checks whether test-set performance is luck or consistent. XGBoost: **0.9686 ± 0.0013** (very stable). |
| **Overfitting flag** | Train R² − Test R² > 0.05 | Random Forest flagged as overfitting (0.9895 − 0.9267 = 0.063 > 0.05). |

## Part 4: How Data Leakage Was Avoided

**Data leakage** means the model accidentally sees test-set information during
training, making it look better than it really is.

We avoided it in two ways:

1. **Train/test split first.** The 80/20 split happens *before* any
   preprocessing. The test set is set aside and never touched during training.

2. **sklearn Pipeline + ColumnTransformer.** The `StandardScaler` (which
   computes mean/std) and `OneHotEncoder` (which learns categories) are both
   *fitted* on training data only. When they transform the test set, they use
   the training statistics — not test-set statistics.

   ```python
   # This is what happens inside pipeline.fit(X_train, y_train):
   #   scaler.fit(X_train_numeric)   <- learns mean, std from train only
   #   encoder.fit(X_train_cat)      <- learns categories from train only
   
   # And inside pipeline.predict(X_test):
   #   scaler.transform(X_test_numeric)  <- uses train mean/std, NOT test mean/std
   #   encoder.transform(X_test_cat)     <- uses train categories
   ```

3. **Label thresholds from training data only.** The Low/Medium/High
   percentile cutoffs are computed on `y_train`, not on the full dataset.

## Part 5: Limitations

1. **Synthetic data, not real surveys.** The dataset is formula-generated.
   Real-world carbon footprint data has much more noise and variance.

2. **High R² is expected, not impressive.** XGBoost's Test R² = 0.9721 means
   the model re-learns the formula. On real survey data, expect 0.5–0.8.

3. **Multi-selects simplified to counts.** `Recycling` and `Cooking_With` are
   encoded as "how many items" rather than "which items". This loses detail.

4. **Tips are rule-based, not SHAP-based.** A better system would compute
   SHAP values per prediction and rank tips by actual marginal contribution.

5. **No regional adaptation.** Emission factors differ by country (e.g., coal
   vs. renewable electricity grids). The model ignores geography.

6. **Target unit.** The raw `CarbonEmission` column is yearly kg CO₂e divided
   by 12 to get monthly. This assumes uniform behaviour throughout the year.

## Part 7: 15 Likely Interview Questions & Short Answers

**Q1. What is R² and what does it mean here?**
R² measures how much of the variance in monthly CO₂e the model explains.
XGBoost's Test R² = 0.9721 means the model explains 97.21% of variance on
the held-out test set. High because the data is synthetically generated.

**Q2. Why did you divide the target by 12?**
The raw `CarbonEmission` column is in kg CO₂e per year. The app collects
monthly inputs, so we convert to monthly by dividing by 12 for consistency.

**Q3. What is data leakage and how did you prevent it?**
Leakage is when test-set information leaks into training. We prevented it by
(1) splitting train/test before any preprocessing, and (2) fitting the
StandardScaler and OneHotEncoder only on training data inside a sklearn
Pipeline. The test set is only transformed — never used to learn statistics.

**Q4. Why did you choose XGBoost over Random Forest?**
XGBoost had a higher test R² (0.9721 vs 0.9267) and lower MAE (10.53 vs
17.45). Random Forest also showed overfitting (train R² 0.99, test R² 0.93).
XGBoost's gradient-boosting corrects errors iteratively, making it more
accurate on this dataset.

**Q5. What is cross-validation and why did you use it?**
5-fold CV splits the training set into 5 parts, trains on 4, tests on 1,
repeats 5 times, and averages R². It checks whether the test-set score is a
fluke. XGBoost's CV R² = 0.9686 ± 0.0013 — consistent and close to test R².

**Q6. Random Forest has 200 trees. Isn't that slow?**
Training takes ~30 seconds on a modern laptop. For inference (one prediction
at a time), Random Forest is fast enough. XGBoost is similar. For serving,
both are sub-millisecond on a single row via `pipeline.predict()`.

**Q7. What does the feature importance chart tell you?**
It shows which features XGBoost used most to make predictions (measured by
Gain — how much each feature reduces the loss when it is split on). Features
near the top of the chart are most responsible for driving predictions.

**Q8. How does the Flask app handle bad inputs?**
The `validate_inputs()` function in `app.py` checks every field:
- Required fields → error if empty
- Categorical fields → error if value not in allowed list
- Numeric fields → error if not a number or outside min/max range
Any error returns HTTP 400 with a list of friendly error messages.
The model is never called if validation fails.

**Q9. What are the Low / Medium / High thresholds based on?**
The 33rd and 67th percentiles of the **training set** target vector only.
Low ≤ 141.00 kg/month (33rd pct), High ≥ 209.25 kg/month (67th pct).
Using quantiles means the labels adapt to the data distribution.

**Q10. The dataset is synthetic. Does that make this project useless?**
Not for learning purposes. It demonstrates end-to-end ML engineering: data
cleaning, pipeline design, leakage prevention, model comparison, evaluation,
Flask deployment, and testing. For a production carbon calculator, you'd need
real survey data.

**Q11. What is MAE vs RMSE? Which should you prefer?**
MAE is the average absolute error — robust to outliers, easy to interpret
("the model is off by X kg on average"). RMSE penalises large errors more
heavily. If a few large errors are very costly, prefer RMSE to track them.
Here, XGBoost: MAE=10.53 kg, RMSE=14.20 kg — RMSE > MAE because there are
some larger errors.

**Q12. Why did you use StandardScaler for numeric features?**
Linear Regression's coefficients are sensitive to feature scale. Without
scaling, a feature with values 0–5000 (vehicle km) would dominate a feature
with values 0–24 (internet hours). Tree-based models (RF, XGBoost) don't
need scaling, but we apply it uniformly inside the pipeline so the same
preprocessing works for all 3 models.

**Q13. What does OneHotEncoder(handle_unknown='ignore') do?**
If a user submits a category value not seen in training (e.g., a future
transport mode), the encoder outputs all zeros for that feature instead of
crashing. This makes the app robust to unexpected inputs.

**Q14. How would you deploy this to production?**
1. Push to GitHub (excluding raw data and .joblib via .gitignore)
2. Create a Render web service with start command `gunicorn app:app`
3. Set environment variables (`SECRET_KEY`, `PORT`)
4. Either commit the pre-trained `.joblib` or add a build step to run
   `python src/train.py` during deploy

**Q15. What would you improve given more time?**
- Use real survey data (e.g., ONS UK Living Costs Survey)
- Add SHAP explanations so tips are ranked per individual prediction
- Add a historical tracker for users to monitor progress over time
- Add geographic input to adjust for regional energy mix
- Containerise with Docker for reproducible builds
- Add CI/CD to auto-retrain when new data arrives
